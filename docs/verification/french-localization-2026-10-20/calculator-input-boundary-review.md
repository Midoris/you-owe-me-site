# French calculator input boundary — independent preparatory review

Reviewed 20 October 2026 by independent `french_technical_review` GPT-6.1 Sol/high model agent. This reviews the proposed contract against the existing calculator/native money model. It does **not** accept the unfinished calculator implementation.

The proposed French-only two-decimal, fail-closed boundary is appropriate. The browser model rounds to cents while native preparation rejects sub-cent input and applies the reviewed rounding/eligibility guards. Accepting French decimal commas, valid space-grouped thousands and canonical dot decimals without changing those algorithms prevents silent separator stripping. Rejecting a sole three-digit comma/dot suffix (`1,234`, `1.234`) is a deliberate, defensible ambiguity rule; clear French help must show `1234`/`1 234` for thousands, `90,50`/`90.50` for decimals and the two-decimal limit. Rejection must remain visible rather than rounding/reinterpreting the field.

Internal grouping should accept only ordinary space, nonbreaking space and narrow nonbreaking space, with a one-to-three-digit first group and exactly three digits thereafter. A broad whitespace expression would also accept tabs/newlines and should not be used. These three equivalent spacing glyphs can coexist when every group is valid; other punctuation, currency text, exponent syntax, control characters and malformed groups must fail. Nonpositive values remain invalid expenses. Outer trimming is compatible with retaining the original raw field/state.

French input elements must use text with decimal input mode so the browser does not discard comma/grouping input before validation. Canonical strings belong only in the cloned state supplied to native preparation. Raw names/descriptions/amount strings, session restoration and retry state must survive untouched. Existing en/es/de parsing, Arabic digit/grouping behavior and financial/native schemas remain unchanged.

Two-decimal format validity does not establish native eligibility. The existing `90.50/3` organizer-credit mismatch and `0.29/2` browser/native rounding mismatch remain withheld; supported `10/3` residual behavior remains eligible. Eight-person `98/8` remains a valid browser calculation and ineligible for the native four-person limit. No locale parser should bypass those guards or convert currency.

Prepared independent fixtures are `calculator-independent-number-fixtures.json`. Final acceptance still requires executing the actual normalizer/runtime, real French text-field entry, exact copied/shared amounts and direction, all prior-language regressions, raw-state cloning/retry/Back tests, mocked consent/transfer behavior and private continuation under effective CSP. No production request/upload or customer data is used for this preparation.
